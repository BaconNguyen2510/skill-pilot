# Proposed blind evaluation harness

**Status: preparation only.** No independent final queries or labels have been supplied and no final evaluation has run. This is a two-stage **adaptation** of `docs/v3/EVAL_FREEZE_PROTOCOL.md`: it reuses the frozen runner's search helper and synthetic catalog, while the old protocol specifies `eval/run_eval.py` with labeled inputs. The independent evaluator and release owner must explicitly accept or reconcile this difference before treating its output as the REL-09 final gate. The adaptation measures the frozen synthetic catalog, not the full installed catalog or actual model behavior.

`harness.py` and `contract.py` are separate from the frozen implementation. All commands below use Python 3.12+ and stdlib. Execute from the repository root. Use a **single, access-controlled, durable, shared ledger** for the candidate, outside the candidate checkout. A separate protected environment should hold labels until the prediction receipt is sealed. The commands are for an independent custodian; do not run the final case set until independence, protocol and thresholds are accepted.

```text
python blind_eval/harness.py catalog
python blind_eval/harness.py validate-queries <unlabeled-queries.jsonl>
python blind_eval/harness.py validate-labels --queries <unlabeled-queries.jsonl> --labels <sealed-labels.jsonl>
python blind_eval/harness.py predict --queries <unlabeled-queries.jsonl> --labels-sha256 <64-hex-commitment> --ledger <protected-existing-directory>
python blind_eval/harness.py score --labels <sealed-labels.jsonl> --ledger <same-protected-directory>
```

`catalog` exposes frozen skill IDs, descriptions and categories, not previous queries, labels, or candidate predictions. `validate-labels` is for the independent label custodian before prediction; it checks query coverage, catalog membership, and at least 30 abstention labels, then prints a SHA-256 commitment. Seal the exact label bytes and give only that digest to the prediction operator. `predict` requires `PYTHONHASHSEED=0` at interpreter startup. In PowerShell, run `$env:PYTHONHASHSEED = '0'` before starting the prediction command. It accepts no label path and passes only query text to the archived candidate. Archive exports source and exposed screening data from commit `2c8daab7ae7a8b06dcfc64863c4043183fd35261`; the receipt binds candidate, scout and evaluator hashes, corpus-builder and exposed-data hashes, harness/contract hashes, runtime, configuration, query bytes and label commitment. Source and dataset bytes are snapshotted before validation and hashing.

An atomic ledger directory is reserved immediately before the first prediction. A failed or interrupted attempt stays reserved; do not delete or replace it to retry. Prediction output is created exclusively, and its digest is bound in a separate receipt. Scoring reserves its own marker before opening labels, checks the commitment and hashes, and never writes to the prediction file. A broken or interrupted scoring attempt also stays reserved. Preserve all files and have the independent evaluator and release owner determine any recovery; a retry requires an explicitly documented protocol decision, not silent deletion.

Exclusive creation and hashes provide write-once behavior in this tool and make changes detectable only while the receipt and ledger are protected. They do not prevent a privileged operator from rewriting both, choosing another ledger, exposing label files through filesystem access, or running another copy of the candidate. Separate accounts/machines or equivalent controls, external timestamped commitments, audit logs, and an independent custodian are required. Do not treat a hash or lexical screening as proof of independence.

## Prospective scoring plan, before final data or results

For an owner-reviewed packet without development results, use `docs/v3/evaluator_packet/`. Exact role-separated commands and still-unaccepted pre-registration decisions are in `docs/v3/FINAL_EVALUATION_ACTIVATION_V3.md`. Archive export explicitly sets `core.autocrlf=false` and `core.eol=lf` per invocation; canonical Git-blob hashes and original Windows-byte hashes are recorded separately. This avoids ambient Git line-ending conversion without changing global configuration or candidate code. Use byte-identical accepted harness/contract files on prediction and scoring machines. Successful `score` execution may write a `FAIL` or `INSUFFICIENT` verdict with exit code zero; inspect `score.json.verdict` and preserve all receipts/failures.

The proposed v1 gate requires at least 200 cases, 100 normalized intent families, 30 cases per `en`, `vi`, `vi_no_diacritic`, `mixed` language, 30 adjudicated abstention cases and 30 cases labeled `multi_intent`. The handoff recommends 50 per language and 40 each abstention/multi-intent as a stronger sampling target. Category and provenance attestations require independent adjudication. Cases may share a normalized intent family for different language slices; near-duplicate queries are screened. All case IDs must appear exactly once in each file.

The primary proposed thresholds are MRR@5 ≥ 0.65, recall@5 ≥ 0.70, forbidden-hit rate@5 ≤ 0.10, and abstention F1 ≥ 0.80. They are fixed in `CONFIG` for this proposed adaptation, not selected after final results, and require acceptance by the release owner and independent evaluator before prediction. Fewer cases or missing required coverage yields `INSUFFICIENT`; a candidate error or failed primary threshold yields `FAIL`. No result authorizes release.

MRR is reciprocal rank of the first relevant result; recall is the fraction of all `relevant` IDs present in the top five; forbidden rate is the fraction of cases with any forbidden ID in the top five. A zero exit with no hits or a structured `INVALID_QUERY` exit 1 is counted as abstention. Other nonzero exits and missing/malformed success payloads are errors, never successful abstentions. Missing/duplicate prediction or label IDs invalidate scoring; none are silently excluded. Relevant and forbidden are independent gold judgments; no automatic substitute/alternate expansion is performed. This differs from the old runner's `required_skills ∪ acceptable_alternates` relevance rule and must be considered when comparing metrics.

Overall and language-slice metrics use a deterministic 2,000-replicate 95% percentile bootstrap of normalized intent-family clusters (seed 42); language CIs are omitted for fewer than two families. Undefined bootstrap replicates are omitted for that metric and intervals may then be conditional; abstention support and TP/FP/FN are reported. Resampling preserves all records in each sampled family; clusters, provenance and sample selection still require independent judgment. Category CIs are not calculated. Secondary reporting includes language and category slices, multi-intent, failure counts, and p50/p95 elapsed search time on the recorded host. Latency has no automatic release threshold because hardware and load are uncontrolled. Structural prompt benchmarks and live model execution are separate evidence, not inferred from retrieval.

No exclusions are automatic after prediction. Invalid/missing inputs, mismatched commitments, unknown IDs, incorrect candidate/harness hashes, and duplicate outputs fail closed; preserve the reason and adjudicate externally. The archived diagnostic comparison reported `recall@5_diff = -0.0076` and must remain visible. There is no final paired baseline on these new cases, so this harness does not claim an improvement over v2.1.0.
